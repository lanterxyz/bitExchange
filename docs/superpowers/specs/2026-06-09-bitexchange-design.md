# bitExchange 完整架构设计

日期：2026-06-09

## 1. 目标

bitExchange 是一套跨终端的聊天式文件互传软件，面向同一人的多台可信设备。它提供类似“微信文件助手”的体验：设备之间可以自动发现、互发文本和文件、粘贴文件到聊天框发送、群发到多个在线设备，并把本机文本聊天记录追加保存到本机 `chat.txt`。

首要目标是高性能文件传输，尽量接近局域网或可用网络链路的满速；同时保证公网信令安全，允许用户按场景选择客户端之间的文件和消息传输是否加密。

## 2. 已确认的产品范围

- 先设计完整多端架构，再拆分阶段实现。
- 不做账号登录体系，采用设备配对码/共享密钥和设备指纹确认。
- 公网 P2P 打洞失败时，允许通过公网服务器中继，但用户可以关闭。
- Web 页面端是轻量临时客户端，不做后台扫描和固定默认路径自动保存。
- 聊天记录只保存本机完整收发记录，不做多设备历史同步。
- 公网信令强制端到端加密，配对时显示设备指纹/验证码。
- 性能优先，安装包体积和资源占用尽量优化，但不牺牲核心传输性能。
- 主要场景是同一人的多台可信设备之间互传。
- 技术方向为高性能核心 + 多端壳层，允许多语言组合。
- 借鉴 Syncthing 的传输原理，但不直接复用或二次开发 Syncthing。

## 3. 总体架构

bitExchange 采用“高性能核心 + 多端壳层”架构。

核心层负责：

- 设备发现
- 设备配对与信任关系
- 端到端信令加密
- 连接路径选择
- P2P / 中继传输
- 文件分块、校验、并发传输和断点续传
- 文本消息日志写入

平台层负责：

- UI 展示
- 系统剪贴板、拖拽、粘贴文件
- 文件选择和接收保存
- 通知、托盘、分享菜单
- 默认保存路径配置
- 平台权限适配

服务端只做信令与可选中继，不保存用户文件，不保存聊天记录，不做账号体系。设备通过配对码/共享密钥加入同一个可信设备组。Web 端定位为轻量临时客户端，只支持配对、文本和文件收发，不承担后台扫描、任意默认路径保存或系统级自动发现。

## 4. 设备发现与连接路径选择

客户端启动后同时进行三类发现。

### 4.1 同子网局域网发现

使用 mDNS 或 UDP 广播发现同一可信设备组内的在线客户端，适合同一 Wi-Fi 或同一网段场景。发现结果只作为候选连接信息，最终仍需通过已配对设备身份校验。

### 4.2 公网信令发现

客户端通过 WSS 连接信令服务器，上报设备 ID、公钥、可达端点、NAT 信息和本机私网 IP 列表。服务器只维护在线状态并转发端点候选信息。

### 4.3 跨层私网探测

信令服务器把双方私网 IP/端口候选地址交换给客户端。客户端收到后主动探测对方私网地址。如果同一站点内不同层级网络可达，则直接走私网传输，避免绕公网。

### 4.4 路径优先级

连接路径按以下顺序选择：

1. 同子网直连
2. 跨层私网直连
3. 公网 P2P 打洞直连
4. 可选公网中继
5. 失败提示

每次传输前选择当前最优路径。连接断开时可以自动降级到下一路径。公网中继作为兜底能力存在，用户可在设置里关闭；关闭后 P2P 失败就提示无法连接。

## 5. 安全与加密

bitExchange 不做账号登录。设备通过一次性配对码或二维码加入同一个可信设备组。配对时生成或交换设备长期公钥，界面显示设备名称、设备指纹或验证码，用户确认后才建立信任关系。后续设备身份以设备 ID + 公钥指纹识别，避免只凭名称误连。

公网信令必须强制端到端加密。客户端通过 WSS 连接服务器，但真正的设备间信令内容还会用设备密钥加密。服务器只能看到必要路由元数据，不能读取配对密钥、连接协商细节或传输控制消息。

客户端之间的消息和文件传输默认不加密，以保证性能；用户可以在会话或发送前切换为加密传输。开启后，文本消息、文件元数据和文件块都加密。未加密模式也只允许在已配对可信设备间使用，不接受陌生设备直接发送。

中继服务器只转发加密后的信令或数据流；如果客户端开启传输加密，中继看到的也是密文。如果用户选择未加密文件传输并且路径降级到公网中继，客户端必须明确提示“文件将经服务器中继且未加密”，让用户选择继续、开启加密或取消。

## 6. 文件与消息传输模型

客户端提供类似微信文件助手的聊天界面：可输入文本、拖拽文件、选择文件、粘贴剪贴板文件或图片到聊天框发送。发送目标可以是单个设备，也可以是同一可信设备组内多个在线设备。群发时每个目标独立建立传输任务，互不阻塞，失败设备单独显示失败原因。

### 6.1 默认本机保存结构

客户端维护一个本机默认保存根目录，默认结构为：

```text
bitExchange/
  chat.txt
  receivedFiles/
```

- 所有本机发送和收到的文本消息，都按时间追加写入默认保存根目录下的 `chat.txt`。
- 收到的文件默认保存到同目录下的 `receivedFiles/` 文件夹。
- 用户修改默认保存路径时，修改的是这个根目录；`chat.txt` 和 `receivedFiles/` 跟随该目录。
- 文件名冲突时不覆盖旧文件，自动生成新文件名。

### 6.2 文本消息

文本消息走轻量消息通道。发送成功后追加写入本机 `chat.txt`；收到后也追加写入本机 `chat.txt`。聊天记录是本机完整收发记录，不做跨设备历史同步。

### 6.3 文件消息

文件消息先发送文件元数据，再进行分块传输。传输层借鉴 Syncthing 的思路，但自研适合“一次性发送”的实现：

- 大文件切块
- 块级校验
- 并发发送
- 断点续传
- 流式读写
- 按连接质量调整并发度

局域网直连优先使用高吞吐流式传输，例如 TCP 或 QUIC。公网 P2P 可优先 QUIC/UDP，必要时降级 TCP 或中继流。第一版不做“文件夹持续同步”，只做用户主动发送的消息和文件。

## 7. 客户端与 UI

所有客户端采用暗黑炫酷风格，核心界面保持一致：左侧是在线设备列表和设备组状态，右侧是聊天/传输窗口，底部是输入框、粘贴/拖拽区域、文件选择按钮、加密开关和发送目标选择。

每个设备显示：

- 在线状态
- 连接路径：局域网、私网直连、P2P、公网中继
- 当前速率
- 最近传输状态

群发时可多选设备。发送后在消息流中显示每个目标的进度。

### 7.1 Windows exe / Linux 客户端

桌面端提供完整能力：

- 局域网发现
- 后台常驻
- 剪贴板文件粘贴
- 托盘
- 默认保存路径配置
- 满速传输

### 7.2 Android APK

Android 端提供完整收发、分享菜单接入、文件选择、通知和二维码配对。后台扫描和默认路径保存需要按 Android 权限模型实现。

### 7.3 Web 页面端

Web 端是轻量临时客户端，支持配对、文本和文件收发、浏览器下载保存。不做后台扫描和固定路径自动保存。

### 7.4 设置页

设置页包含：

- 设备名称
- 默认保存根目录
- 是否允许公网中继
- 传输加密默认值
- 信令服务器地址
- 可信设备管理
- 日志位置

UI 不暴露 Syncthing 的“文件夹同步”概念，只呈现“聊天式发送”。

## 8. 服务端设计

服务端分为两个逻辑模块：信令服务和可选中继服务。

### 8.1 信令服务

信令服务通过 HTTPS/WSS 提供：

- 设备上线
- 心跳
- 在线状态
- 端点交换
- NAT 信息交换
- 私网 IP 候选地址分发
- 连接协商消息转发

所有敏感信令内容由客户端端到端加密。服务端只依据设备组路由必要的密文消息。服务端不保存聊天记录、不保存文件、不提供账号登录。

### 8.2 中继服务

中继服务只在客户端直连失败且用户允许中继时启用。它负责转发数据流，不解析业务内容。如果客户端开启传输加密，中继看到的也是密文。

服务端应限制单连接资源占用，支持限速和配额配置，并提供基础运行指标，例如在线设备数、连接尝试数、中继流量和错误率，便于部署者观察状态。

### 8.3 部署形态

服务端优先设计成单个轻量二进制程序。配置项包括：

- 监听地址
- TLS/WSS 配置
- 中继开关
- 最大连接数
- 流量限制
- 日志级别

后续可以拆分信令和中继，但第一版保持一个服务端程序更简单。

## 9. 技术栈与打包

### 9.1 核心传输和协议层

优先使用 Go。原因是 Go 适合网络编程、并发、跨平台编译、单文件二进制、低资源占用，也便于借鉴 Syncthing 的传输思想。

### 9.2 服务端

服务端使用 Go 单二进制，包含 WSS 信令和可选中继。

### 9.3 桌面客户端

桌面客户端优先考虑 Tauri + Web UI + Go 本地核心进程。这样能兼顾较小安装体积、良好 UI 开发效率和高性能传输核心。如果后续 UI 跨 Android 复用更重要，再评估 Flutter。

### 9.4 Android 客户端

Android 客户端使用 Kotlin/Compose UI，并通过 gomobile 或本地服务方式集成 Go core，以便处理 Android 权限、分享菜单和通知。

### 9.5 Web 轻量端

Web 轻量端使用 TypeScript 前端，通过 WSS、WebRTC 和浏览器文件 API 接入。能力受浏览器限制，不能等同原生完整客户端。

### 9.6 GitHub Actions 产物

GitHub Actions 自动构建目标：

- Windows：安装包或便携 exe
- Linux：AppImage、deb 或 tar.gz 中至少一种
- Android：APK
- Server：Linux amd64/arm64 二进制
- Web：静态资源包或随服务端嵌入发布

## 10. 测试与验收标准

### 10.1 局域网直连

两台同子网设备能自动发现，互发文本和文件。文本追加到本机 `chat.txt`，收到文件保存到 `receivedFiles/`。大文件传输速度应接近网络和磁盘上限。

### 10.2 跨层私网直连

两端通过公网信令交换私网候选地址后，如果私网可达，应自动优先走私网路径。

### 10.3 公网 P2P 与中继

不同 NAT 环境下先尝试 P2P，失败后在用户允许中继时自动走中继。用户关闭中继时给出明确失败原因。

### 10.4 安全

配对必须显示设备指纹或验证码。公网信令为端到端密文。未加密文件经公网中继前必须提示。

### 10.5 多端

Windows、Linux、Android、Web 至少能完成配对、文本发送、文件发送和接收。Web 明确只作为轻量临时端。

### 10.6 群发

多选多个在线设备后，能并行发送并分别显示每个目标的进度和结果。

### 10.7 打包

GitHub Actions 能产出 Windows、Linux、Android、Server、Web 构建产物。

### 10.8 性能

性能测试至少覆盖：

- 1GB 大文件
- 多个小文件
- 局域网千兆环境
- 中继降级环境

核心协议和传输层做自动化单元测试与集成测试。网络路径选择做可模拟 NAT/中继的集成测试。UI 做关键路径手工验证和少量端到端测试。

## 11. 分阶段建议

虽然本设计覆盖完整多端架构，实施应分阶段进行：

1. Go core + Go server 基础协议、配对、局域网发现、文本和文件直连传输。
2. Windows/Linux 桌面客户端，完成聊天式 UI、路径配置、`chat.txt` 和 `receivedFiles/`。
3. 公网信令、P2P 候选交换、跨层私网探测和可选中继。
4. Android APK，完成配对、收发、分享菜单和通知。
5. Web 轻量端，完成临时配对、文本和文件收发。
6. 性能优化、加密传输开关、GitHub Actions 多平台打包。
