bitExchange 架构路线对比

基于你选择的方向：完整多端架构、无账号配对、允许可关闭中继、Web 轻量、信令端到端加密、性能优先、同一人可信设备、借鉴 Syncthing 原理。

方案 A：高性能核心 + 多端壳层（推荐）
Windows/Linux
桌面 UI
Android UI
Web 轻量页
↓ 调用统一核心协议/传输库 ↓
Go/Rust Core：发现、配对、加密、P2P/Relay、文件块传输
↔
Signaling/Relay Server：上线、端点交换、可选中继

A. 高性能核心 + 多端壳层

核心能力统一，桌面/Android/Web 只做平台适配；性能和长期维护最平衡。

方案 B：基于 Syncthing 二改
Syncthing 发现/中继/传输/同步模型
↓ 大量改造 ↓
聊天式发送、群发、粘贴文件、移动端/Web 适配

B. 基于 Syncthing 改造

能借到成熟传输经验，但同步模型和聊天式互传差异大，改造成本和耦合高。

方案 C：Web/Electron 优先
Electron/Tauri/Web UI
↓
JS/Node 传输 + WebRTC + Server Relay

C. Web 技术优先

界面开发快，但局域网扫描、后台保存、满速大文件传输和移动端权限更受限。

推荐 A 的原因

  • 传输核心可直接针对满速优化
  • 桌面、Android、Web 能共享协议和安全模型
  • 保留借鉴 Syncthing 原理的空间，不被同步模型绑死

主要代价

  • 初期工程拆分比单框架更复杂
  • 需要明确 FFI/本地服务/API 边界
  • 多平台打包需要较早规划 CI
